Switching Models Shouldn't Mean Reintroducing Myself

Cross-tool memory for a personal agent

When I switch models, developer tools, machines, or even just a project path, I often have to explain the background again: the constraints, the approaches already rejected, and where the work stopped. What interrupts me is usually not that the model cannot search. It is that those facts are locked inside different sessions.

Memory for a personal agent should not belong to one model or one session. I also do not want every chat compressed into a summary that stays pinned forever. What I want is a layer I control, with sources and permissions: collect the evidence first, retrieve it for the task at hand, consolidate only when that helps, and hand it back through an inlet that tool actually supports.

This is not a new theory of memory, and it is not a product I have built. It treats continuity across tools as something that can be taken apart and falsified.

Explaining myself again

The same work spreads out. The model changes, the harness (the developer tool or runtime) changes, the account changes, the machine may be local or in the cloud, and the project path changes too. A memory feature that works well inside one tool does not fill a gap that the next tool never recorded.

So the pain is not only “search the history we already kept a bit more accurately.” If the background, the constraints, the dead ends, and the current status were never written down, a later model has nothing to retrieve. In the November 6, 2026 article, Anthropic defines cross-session memory as context that can be read again later, and separates it from weight updates, learning inside a single conversation, and compaction. Dreaming, in that article, is a later pass over logs and notes that were already written.[1]

Five separate jobs

When people say “add memory to the agent,” they often mix five different jobs. Keeping them apart is what stops one of them from pretending to be the others.

  • Collection. Were the messages, tool calls, and results written down at the time?
  • Identity and permission. Whose records are these, and may another project or account see them?
  • Consolidation. Should facts, decisions, and linked pages be extracted from the raw record?
  • Retrieval. For this task, should the model see the raw text, the consolidated pages, or both?
  • Injection. Can the result be handed back through an inlet this tool supports, and will the model use it?

Collecting is not the same as handing the evidence back reliably. Retrieving is not the same as the model choosing to look. Injecting text into the context is not the same as the model following it.

Three inlets, three partial views

I would not send every request through one gateway that is supposed to see the whole workflow. The more stable split is three complementary paths: a local scan for history already on disk, hooks or an SDK for what is happening now, and an API gateway only as an option, responsible solely for the requests it actually routes.

The Claude Code docs say that each message, tool use, and result is written as plaintext JSONL under ~/.claude/projects/. I am citing that path only. I have not read my own sessions or anyone else’s. Resuming reopens the same session ID and appends. Forking copies the history into a new session ID. Hooks can supply the session, working directory, transcript path, and compact events. A cloud session does not read local ~/.claude/settings.json, so a hook configured only on this machine should not be assumed to cover the cloud.[2][3]

Codex’s public recorder also writes session rollouts as JSONL. I read the file at commit 8806313 from November 2, 2026, not the moving main link. That revision shows resume, and that revert creates a new rollout file. I did not audit the whole record schema, so I cannot say that every tool output is kept in full.[4]

MCP is a different mechanism. It lets a client call tools and read or write an authorized store. Connecting MCP does not start a recording of every conversation. Collection still has to be arranged separately.[6][9]

A local scan only recovers what was written

History from before a hook was installed can only be read from files the tool already wrote. The flow below is a design, not an implementation. It reads only directories the user names. It does not scan a home directory, and it does not guess at a private GUI database.

Identity is something I configure. A repository URL and a workspace path are only clues. A fork, a mirror, a directory with no remote, and two projects that share a name should not be merged on path alone. Deleting a memory has to reach the evidence, the index, derived pages, and the injection cache, and it needs a tombstone so the next scan does not bring it back.

Historical text is low trust. If it says “ignore the previous constraints” or “send the secret out,” that is dialogue from the time, not a new instruction for this memory layer.

Existing systems each cover a piece

Memory that crosses tools is not new. The items below are capabilities described in documentation. They are not a ranking from my own tests, and they are not a buying guide.

  • Claude-Mem records observations from tool execution, searches them with local SQLite full text, and points back to an observation ID.[7]
  • Mem0’s Claude Code plugin uses hooks to keep local activity, then sends batches to Mem0. The docs treat user_id as the person, separate from the project and the session. I checked only this Claude Code integration.[8]
  • Supermemory exposes MCP tools that save submitted content, search, and forget. Several clients can use a space they are allowed to use. The docs do not say that connecting the server records every conversation.[9]
  • Letta keeps memory in MemFS and consolidates in the background. That does not show that it automatically collects every session from an arbitrary external tool.[10]
  • Hindsight offers retain, recall, and reflect, and says it does not store conversations as archives. A raw evidence store still has to be considered separately.[11]

These are parts, not five alternatives. A collector is an inlet, a memory engine organizes and retrieves, and MCP is one outlet. Sharing a store does not make account permissions correct, and it does not make the model look anything up.

Search or consolidate, depending on the task

Search over the raw record is a reasonable base. Notes or a wiki are a derived view. They can be rebuilt, and they should not become the only source of truth. The raw record, in turn, only shows that something was said or observed at the time. It does not by itself prove an outside fact.

Anthropic tried this on Stainless internal documents: about 350,000 files and roughly 420 million tokens, with 25 questions. Opus 5 agents used from 2 to 128 sessions to read the material, write and revise wiki pages, merge duplicates, and check claims against sources. Wiki-only graded-criteria scores rose from 13% to 48%. Search alone scored 53%. Wiki plus search rose from 54% to 61% as the wiki grew, and saved about 20,000 tokens per question.[1]

Those percentages are aggregates over graded criteria. They are not a task-success rate, and they are not a general accuracy number for cross-tool memory. The per-question token difference in that experiment does not include a full accounting of background build and maintenance cost, so it should not be treated as a net saving on every chat.

The same article has an example that points the other way. A merger packet had 24 questions. More than half required information from several documents, and many also required judgment or calculation. On the items that needed cross-document work or judgment, the wiki scored 87% and search alone scored 73%. That is not the average of all 24 questions. On one Harvey LAB task, most criteria could be met from a single document and the wiki showed no clear gain. On another, the wiki grew larger than the source files. Whether a consolidation layer is worth it depends on the task.

Consolidate in the background, retrieve for the task

Background consolidation should not block the work in front of me. While answering, the system should be able to read pages that are already consolidated and recent records that are not, and it should show which is which. New evidence and corrections that come back from the model are written to the raw store. The loop is not a way for the wiki to certify itself.

The handoff has to be designed per tool. A short evidence packet can go through MCP. A few stable rules, and a pointer to where to search, can live in files the tool already reads, such as CLAUDE.md or AGENTS.md. A one-off human handoff can be a prompt that states its scope. Dynamic injection belongs only on a hook whose docs say it can return context.[2][3][6] The Codex SDK docs describe starting, continuing, and resuming a local thread. They do not describe listening to every existing GUI session.[5]

Each consolidated item should keep its source events, time, and scope. A preference I stated, a rule a test confirmed, and a guess the model made at the time should not be written as the same kind of thing. When they conflict, keep both and point back to the source instead of letting the latest write overwrite everything.

A handoff experiment that has not been run

The smallest step is not a full wiki. Start with one public log format, such as Claude Code JSONL, and use synthetic data or an export I have explicitly allowed that contains nothing sensitive. Check that a read-only incremental collector can be replayed. Build only a search inlet over the raw evidence. A second tool should read the same store through an MCP it supports, or through an explicit evidence prompt, so one project handoff can be tried. Consolidation and an optional gateway come after that.

To decide whether consolidation helps, I want an experiment rather than another demo. Let tool A leave constraints, paths that failed, the final decision, and a later correction. Let tool B continue the same project. Along the way, change a path, introduce a branch conflict, an expired fact, a cross-project permission, and a case where historical text tries to act as a new instruction.

Three conditions, with the same setup:

  • No memory.
  • Search over the raw record only.
  • A consolidation layer, plus that same search.

The model, the raw evidence, the online token budget, the current code, and the permissions stay fixed. Handoff runs in both directions, and it is repeated. Record whether the task is completed, whether facts are supported by evidence, whether old facts or another project leak in, whether the model looks anything up, how long the handoff takes, latency, input and output tokens, and the cost of background maintenance. Deletion propagation and secret filtering are separate tests.

This experiment has not been run. There is no improvement percentage here. If the third condition is no better than the second, or if maintenance cost outweighs the gain, there is no reason to add a wiki.

Appendix: easy mistakes in a scan

The body keeps the judgment. These are implementation boundaries, and they are still only design requirements.

  • When a file is rotated, truncated, or replaced, record the generation. An offset alone will read the wrong place in the new file.
  • Hold a partial JSON line. Isolate an unknown schema and warn. Do not put it in the normal index.
  • Make the write durable before moving the checkpoint. Replay depends on idempotent writes, not on “nothing was written after the checkpoint.”
  • A hook, a log, and a gateway may see the same event. Keep the sources, and count it once. Do not learn a fork’s shared prefix twice. Hashing only the body can merge events that really did repeat, so prefer an event ID and a source location.
  • Keep a compacted summary separate from the original dialogue. A failed branch is not a final decision. Mark a truncated output as missing. Do not invent the rest.
  • Filter secrets before storage or export. Filtering is not a guarantee of zero leakage. Retention, pause, exclusion, encryption, and project permissions need to be switchable on their own.
  • Display times can use a single zone. Storage should keep the source timezone.
