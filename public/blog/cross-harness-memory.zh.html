换一个模型、换一个开发工具、换一台机器，甚至只是换了项目路径，我经常得把背景再讲一遍：约束是什么，哪条路已经否决，项目现在停在哪。打断我的通常不是模型不会搜，而是这些东西被锁在不同的会话里。

个人 Agent 的记忆，不该只属于某一个模型或某一个 session。我需要的也不是把所有聊天压成一段永远置顶的摘要。更想要的是一层由我控制、带来源和权限的上下文：先把证据收下来，再按任务去检索，必要时再整理，最后从每个工具自己支持的入口交还给模型。

这不是一套新的记忆理论，也不是我已经做出来的产品。它只是把跨工具的连续性当成一件可以拆开、也可以证伪的事。

又要重讲一遍

同一件事会散在好几个地方。模型不同，harness（开发工具或运行框架）不同，账号不同，本地和云上的机器不同，项目路径也会变。单看某一个工具里的记忆做得再好，也补不上下一个工具里根本没有的那一段。

所以痛点不是“在已经记下的历史里再搜得准一点”这么简单。背景、约束、走过的弯路和当前进度，如果没有被记下来，后面的模型无从检索。Anthropic 在 2026 年 11 月 6 日的文章里把跨 session 的记忆和权重更新、单次会话里的学习、以及单纯的 compaction 分开：后台回看只能处理已经留下的日志和笔记，不能恢复从未记录的经历。[1]

先拆开五件事

人们说“给 Agent 加 memory”时，经常把五件不同的事混在一起。分开看，后面的设计才不会互相代替。

  • 采集。当时的消息、工具调用和结果有没有留下。
  • 身份和权限。这些记录属于谁，能不能被另一个项目或另一个账号看见。
  • 整理。要不要从原始记录里抽出事实、决策和互相链接的页面。
  • 检索。面对眼前这个任务，该查原文、查整理后的页面，还是两者一起查。
  • 回填。查到的东西能不能通过这个工具支持的方式交回模型，以及模型会不会用。

能采集，不等于能可靠地交回去。能检索，不等于模型会去查。注入进上下文，也不等于它会遵守。

三条入口，各看见一块

我不会把所有流量都送进一个什么都能看见的网关。更稳的是三条互补的路：本地扫描补已经落下的历史，hooks 或 SDK 补正在发生的事，API 网关只作为可选项，并且只对自己路由过的请求负责。

Claude Code 的文档写明，消息、工具调用和结果会以明文 JSONL 落在 ~/.claude/projects/ 下面。我只引用这个路径，没有去读自己或别人的会话。同一会话 ID 上 resume 是追加，fork 会把历史复制到新 ID。Hooks 能提供会话、工作目录、记录路径，以及 compact 等事件。云上的会话不读本机设置，所以不能假设本机 hook 会自动覆盖云端。[2][3]

Codex 的公开 recorder 也会把 session rollout 写成 JSONL。我看的是 2026 年 11 月 2 日的提交 8806313，不是会随时变化的 main 链接。那里能看到 resume，以及 revert 会换一个新的 rollout 文件。我没有把整份 schema 审计完，所以不能说每个工具输出都被完整留下。[4]

MCP 是另一回事。它让客户端调用工具、读写一块被授权的信息，但接上 MCP 并不等于开始录制所有对话。采集仍然要另外安排。[6][9]

本地扫描只补已经写下的历史

如果要补安装 hook 之前的会话，只能读工具自己已经落下的文件。下面是一条还没实现的扫描流程。它只读用户点名的目录，不扫整个家目录，也不去猜图形界面的私有数据库。

身份由我显式配置。仓库地址和工作区路径只是线索。fork、镜像、没有 remote 的目录、以及两个同名项目，都不能靠路径自动合并。删掉一段记忆，要同时删证据、索引、整理出来的页面和注入缓存，并留下删除标记，避免下次扫描又把它找回来。

历史文本的信任级别很低。里面如果写着“忽略之前的约束”或“把秘密发出去”，那是当时的对话，不是这个记忆层的新指令。

已有系统各管一段

跨工具的记忆并不新。下面这些是文档里写明的能力，不是我自己测过的排名，也不是购买建议。

  • Claude-Mem 用生命周期采集，再在本地做检索，并用观察 ID 指回原文。文档也写了：有的客户端只能搜，不能录。[7]
  • Mem0 的 Claude Code 插件 用 hooks 在本地捕获，再批量提取。跨机器要自己设置 user id。我只核过这条 Claude Code 集成的说明。[8]
  • Supermemory 通过 MCP 保存、搜索和忘记。多个客户端可以访问同一个授权空间，但连接本身不会自动记下所有对话。[9]
  • Letta 用文件系统式的记忆，并在后台做巩固。这不能证明它会自动采集任意外部工具的全部会话。[10]
  • Hindsight 做保留、回忆和反思，并说明自己不以完整会话档案为存储目标。原始证据仍然要另外留。[11]

它们更像零件，而不是五选一。采集器是入口，记忆引擎管组织和检索，MCP 是一个出口。共享一个库，不等于账号权限就是对的，也不等于模型会主动去用。

检索和整理，谁先谁后

原始记录上的搜索，是比较稳的底座。笔记或 wiki 是从这些记录派生出来的视图，可以重建，不该变成唯一的真相。反过来，原始记录也只证明当时说过或看到过，不自动等于外界事实。

Anthropic 用 Stainless 的内部文档做了一组很小的试验：大约 35 万个文件、4.2 亿 tokens，一共 25 个问题。Opus 5 用 2 到 128 次会话去读材料、写和改 wiki、合并重复并回源核对。只靠 wiki 时，评分标准的合计分数从 13% 升到 48%。只给搜索工具是 53%。wiki 和搜索一起用，随着 wiki 变厚，从 54% 到 61%。一起用时，每题大约少 2 万 tokens。[1]

这些百分比是评分细则的合计，不是“任务做成了多少”，更不是跨工具记忆的通用准确率。该实验中的每题 token 消耗差异，未在此给出后台构建/维护的完整摊销，所以不能把它当成每次聊天的净节省。

同一篇文章里还有一个方向相反的例子。并购材料的 24 个问题里，超过一半要跨文档，不少还要判断或计算。在那些条目上，wiki 是 87%，只搜索是 73%。这不是 24 题的总平均。Harvey LAB 里另有一道题，多数标准从单篇文档就能检索到，wiki 没有明显好处。还有一道题，wiki 比原文还大。所以整理层是不是值得，要看任务，不能先站队。

整理在后台，检索在眼前

后台整理不该挡住手头的工作。在线回答时，既要能查已经整理好的页面，也要能查还没整理的近期记录，并且让人看得出新旧。模型交回来的新证据和修正，再写回原始库。这个环不是让 wiki 自己证明自己是对的。

交回去的方式也得分开。短的证据包可以走 MCP。少量稳定的规则和“去哪检索”的说明，可以放进 CLAUDE.md、AGENTS.md 这类工具本来就会读的文件。一次性的人工交接，用一段写明范围的 prompt 就够。只有文档写了支持上下文输出的 hook，才做动态注入。[2][3][5][6]

整理出来的每一条，都该留着来源事件、时间和生效范围。我明确说过的偏好、测试证实过的规则、模型当时的猜测，不要写成同一种东西。冲突时先并列并指回原文，不要用最后一次写入覆盖一切。

一个还没做的交接实验

最小的一步不是先做完整 wiki。先接一种有公开格式的日志，例如 Claude Code 的 JSONL，用合成数据或我明确授权的、不含敏感内容的导出，验证只读、增量、可重放。先只做一个原始证据的搜索入口。第二种工具通过它支持的 MCP，或一段显式证据 prompt，去读同一个库，看一次项目能不能交接。整理层和可选网关放在这之后。

真要判断整理有没有用，我希望看到这样一个实验，而不是再添一个演示。让工具 A 留下约束、失败过的路径、最终决定，以及后来的纠正。再让工具 B 在同一项目上接着做。中间加入改路径、分支冲突、过期事实、跨项目权限，以及把历史文本当成新指令的情况。

三组对照用同一套条件：

  • 没有记忆。
  • 只对原始记录做搜索。
  • 整理层，加上同一个搜索。

模型、原始证据、在线 token 预算、当前代码和权限都固定。两个方向都交接，并重复跑。要记的是：任务是否完成、被证据支持的事实是否准确、旧事实或别的项目有没有污染进来、有没有主动去查、交接花了多久、延迟、输入输出 tokens，以及后台维护的成本。删除能不能传遍各处、秘密过滤会不会漏，另做单测。

这个实验还没有跑。所以这里没有提升百分比。如果第三组并不比第二组好，或者维护成本盖过收益，就不必上 wiki。

附录：扫描时容易做错的几件事

正文只保留判断。下面这些是实现时的边界，仍然只是设计要求。

  • 文件被轮转、缩短或替换时，要识别代次。只保存字节偏移，会在新文件上读错位置。
  • 半行 JSON 先暂存。未知的 schema 单独隔开并告警，不塞进正常索引。
  • 先把记录写稳，再提交检查点。重放靠幂等，而不是靠“检查点之后一定没写过”。
  • hook、日志和网关可能看到同一件事。保留多份来源，但只算一次。fork 的公共前缀不要学两遍。只靠正文哈希，可能把真的重复事件误并成一条，所以优先用事件 ID 和来源位置。
  • 压缩摘要和原始对话要分开。失败分支不能升级成最终决定。被截断的输出标成缺失，不臆补。
  • 秘密过滤要发生在入库或外发之前。过滤不是零泄漏保证。保留期限、暂停、排除、加密和项目级权限要能单独关掉。
  • 展示时间可以用北京时间，存储仍保留来源时区。
