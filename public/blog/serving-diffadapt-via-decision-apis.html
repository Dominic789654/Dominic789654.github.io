The Free Lunch in Decision APIs

One Prefill, Two Uses

  1. Separate interfaces need not duplicate computation
  2. The tightest integration reads from the same prefill
  3. Prompted decisions can share most of the work too
  4. The engine should make shared state explicit
  5. Measure marginal cost and decision utility separately
  6. One computation can have more than one output

Decision APIs and chat APIs look like different products. One returns a category, a score, or a Boolean judgment; the other generates an answer. Inside an ordinary causal generative language model, however, they can begin with the same kind of computation: prefill the input, obtain model representations, and read an output.

That suggests a simple opportunity. If a chat request already needs a prefill pass, why not obtain a decision from that computation as well?

The idea is not to place another judgment model in front of chat, or to call a decision endpoint and then send the same input through chat again. The more interesting path is inside the engine: share the target model's prefill and obtain a control signal alongside the state needed to generate an answer. With sufficiently good engine support, the decision's marginal cost could become small enough to approach a free lunch.

What becomes nearly free is the additional decision, not the prefill that chat already requires. This note proposes that execution model and how to test it.

Separate interfaces need not duplicate computation

Before autoregressive chat begins generating, it processes the input and builds state for decoding. A label-scoring decision also processes an input, then reads candidate-label scores at a designated position, without needing to generate an explanation.

SGLang's decision documentation provides a concrete example. An ordinary generation model can answer typed questions through /v1/decisions, using the prefill scoring path of /v1/score to obtain next-token scores for the labels. Decisions do not inherently require a separate computational mechanism from chat.

If two requests execute independently without reusing their common prefix, the system pays to process that input twice: once to decide, and once to answer. A cleaner API wrapper does not eliminate the duplicated work.

If the requests use the same model and share an identical token prefix, however, that repeated computation can potentially be combined. The most interesting efficiency opportunity in decision APIs may be reusing the prefill cost already paid by chat, rather than simply generating fewer output tokens.

The tightest integration reads from the same prefill

A direct design retains two outputs of one prefill: the KV state needed to continue chat and the final-position hidden representation needed by a decision readout.

A lightweight control head consumes that representation and returns a policy signal. The engine applies supported settings, such as an output budget or sampling parameters, and continues decoding from the original KV state. The request does not need another complete pass over the input, or a textual judgment that must be generated and parsed.

The cost structure is straightforward. Beyond chat's existing prefill and decoding work, the system adds a small readout and control logic. If these are sufficiently lightweight, the decision becomes a byproduct of chat prefill.

DiffAdapt provides evidence that this can work for one useful signal: a lightweight probe on prefill hidden states can select a reasoning strategy. The representation formed while reading the question already contains information useful for controlling subsequent inference. DiffAdapt supports the feasibility of reading decisions from existing representations; it is not the main subject here, nor proof that every decision can be read reliably from the same state.

A particular control head still needs suitable training or validation. Ordinary next-token logits at a chat position do not automatically answer arbitrary decision questions. The opportunity is to let a meaningful readout reuse an existing representation instead of rerunning a long prefill merely to obtain a control signal.

Prompted decisions can share most of the work too

A general decision API often needs an additional question and candidate labels. For example, the input may be a long conversation, followed by a question asking which execution strategy to use. The decision branch and the answer branch will not usually have identical final hidden states, but they can still share the preceding long prefix.

Let the common prefix be P. The engine computes P and retains its KV state. A decision branch appends a short suffix D, processes D, and reads the label scores. Once the policy is available, the answer branch resumes from the retained state of P, processes its own suffix C, and generates the answer. D is used only for the decision; it does not become part of the answer branch's context. P must already contain the complete request needed to make the decision. C contains only answer formatting or post-decision steering, not task information that the decision has yet to see.

The incremental work is then primarily the decision suffix, its readout, and branch management, rather than another pass over all of P. The suffix still attends to prefix state, so its cost depends on context length. But it does not rerun the full forward computation for every prefix token. This is particularly worth exploring for long inputs and short decision questions.

SGLang already supports prefix reuse, and its decision documentation explicitly describes cached-prefix reuse by subsequent scoring requests. These existing capabilities establish label scoring and prefix reuse, not an already-implemented atomic route of the kind proposed here. Prefix caching is nevertheless different from an atomic decision-then-chat execution. The proposed integration should explicitly retain shared state, execute the decision branch, and continue the answer, rather than relying only on two independent HTTP requests happening to hit a cache.

The engine should make shared state explicit

The important interface may not be another URL. It may instead be an engine request that says: process this context, read these control signals, and continue answering from the resulting state.

Three boundaries need to be defined.

The sharing boundary. Prefix-cache implementations match actual token prefixes. Reuse requires a common prefix with matching tokens, positions, and attention conditions under the same model weights and adapter configuration. A decision checkpoint with different backbone weights or attention configuration cannot directly reuse chat KV, and noncausal attention does not become compatible just because the API shape matches (SGLang documents prefix caching as disabled for noncausal_full_attention). Semantically equivalent inputs with different templates may share little computation. Placing the decision question after the common context can preserve a longer shared prefix. If a policy changes an earlier system prompt, the affected cache state cannot simply be reused.

The readout boundary. SGLang’s request and scheduling implementation distinguishes cache matching from output-score computation. KV cache is state for subsequent attention; it is not a store from which all hidden states or final logits can automatically be recovered. A direct control head needs the engine to retain or immediately consume the appropriate representation when prefill finishes. Label scoring needs a readout at the correct decision position. Doing this where the state already exists avoids recomputation just to retrieve an output.

The control boundary. A signal must be available before the action it controls. Output budgets and other supported decoding settings can be applied before generation; other adjustments depend on the engine and model. The decision module supplies a signal, and the engine connects it to a control point where it can actually take effect.

This is the essential difference from attaching a separate classification service. Shared prefill places the decision where the model's state already exists. A separate service must acquire the information needed to understand the input again.

Measure marginal cost and decision utility separately

Two questions establish whether the idea works: was computation actually reused, and was the resulting decision useful?

To measure reuse, compare three paths under the same model and workload: independent decision and chat execution, two requests using prefix caching, and explicit engine-level fusion. Hold the readout mode, decision rule, and prompt tokenization fixed across all three paths: comparing a trained head with a prompted decision would confound the engine comparison. Relative to chat without a decision, measure additional prefill work, time until the decision is available, time to first token, throughput, and the overhead of retaining state. Measure time to first token from request arrival, including the wait for the decision, and throughput as completed requests per second under a fixed workload. Report cold and warm caches, cache hit rate, actual recomputed token counts, and retained-KV occupancy. Vary input length, decision-suffix length, and concurrency rather than selecting only one favorable case.

To measure utility, test a concrete control task. For example, does a reasoning-strategy signal reduce generation work while preserving answer quality? DiffAdapt supplies one possible task and baseline. Other decisions about the existing context could use the same execution pattern, but each needs its own validation; one successful probe cannot validate every readout.

If fused execution adds little overhead to ordinary chat, and the signal saves subsequent computation, the free lunch has empirical support. No inference pass disappears by magic. A prefill that previously served only generation now serves a decision as well.

One computation can have more than one output

Chat and decisions can remain separate product interfaces without independently processing the same input at execution time.

One prefill can prepare the state for an answer and provide a decision signal. That is the central opportunity. DiffAdapt shows that one class of useful signal can already be extracted from prefill representations. Decision APIs provide a convenient output form. The engine's job is to make the underlying computation genuinely shared.

With that support, a decision need not always cost another model call. It can be another result of computation that chat was going to perform anyway.

An execution-model proposal; no new performance experiments are reported here.
